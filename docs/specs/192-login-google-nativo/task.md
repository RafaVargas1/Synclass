## Inconsistências encontradas (resolvidas por Claude antes da implementação começar)

1. **Rascunho citava "Expo SDK 53"** — errado, o projeto está na SDK 57 (`frontend/package.json`, `expo: ~57.0.18`). Corrigido no item de verificação de compatibilidade acima.
2. **`.env.example` novas variáveis, destino não decidido no rascunho**: não existe `frontend/.env.example` no repo (confirmado por busca) — as únicas variáveis relacionadas ao Google hoje ficam em `.env.example` da raiz (`GOOGLE_CLIENT_ID`, usada pelo backend). Decisão: `EXPO_PUBLIC_GOOGLE_IOS_CLIENT_ID` (e, se necessário, `EXPO_PUBLIC_GOOGLE_ANDROID_CLIENT_ID`) vão no `.env.example` da raiz, junto das demais — mesmo lugar de todo o resto, sem criar arquivo novo. `EXPO_PUBLIC_GOOGLE_CLIENT_ID` (o "web client id") **já deveria existir** no frontend hoje (é usado pelo fluxo web, issue #65) — se não estiver documentado no `.env.example` da raiz, adicionar também (débito da issue #65, não desta Task, mas corrija se notar a lacuna).
3. **Forma exata da API do `@react-native-google-signin/google-signin` não confirmada com certeza total**: pesquisa nas docs oficiais confirmou (a) usar essa lib, não `expo-auth-session`; (b) `webClientId` no `configure()` precisa ser o mesmo Client ID "Web application" já usado no backend, para o `aud` do idToken bater com `ValidadorDeIdTokenGoogle`. **Não confirmado com certeza**: se `GoogleSignin.configure()` é síncrono ou retorna Promise, e se `GoogleSignin.signIn()` (na versão que o `expo install` de fato baixar) lança exceção com `error.code === statusCodes.SIGN_IN_CANCELLED` no cancelamento (padrão de versões mais antigas da lib) OU devolve um objeto com união discriminada tipo `{ type: 'cancelled' }` (mudança de API em versões mais recentes, v13+, ligada à nova Credential Manager API do Android) — **verificar contra o código-fonte/typings real da versão instalada antes de escrever o mapeamento de cancelamento**, não assumir nenhum dos dois formatos como certo sem checar. Ver `implementation.md#ponto-de-inserção-exato`.

## Inconsistências encontradas (por este harness, durante a implementação)

1. **Item 7 (log estruturado)**: `GoogleLoginSolicitado`/`GoogleLoginSucesso` **não existem** no código do fluxo web atual — grep não encontrou nenhuma ocorrência fora dos próprios docs desta Task (`google.ts`/`useAutenticadoGoogle.ts` não têm eventos de log; o frontend não tem mecanismo de log estruturado). O texto do item pede "nenhum código novo", então não há o que adicionar nem reutilizar — não foi escrito nenhum evento (não se inventa nome que o usuário não vê em lugar nenhum, ver guideline de rótulos/mensagens).
2. **Item 3 (teste de `useAutenticadoGoogle` com caminho nativo)**: a descrição pede "mock do SDK + mock de `obterIdTokenGoogle` retornando idToken — cobre que a sessão é criada e chama o backend", mas o `useAutenticadoGoogle` atual **não** usa `obterIdTokenGoogle` nem chama backend — ele apenas recebe o resultado já pronto (`{ token, nome, papeis }`) via `handleAutenticadoGoogle` e persiste a sessão via `useSessao().definirSessao` (que grava no dispositivo, não no backend). O `implementation.md` (fonte de decisão) confirma que `useAutenticadoGoogle` **não muda** nesta Task. O critério de aceite associado ("Sucesso: sessão criada, cai no Painel") **já é coberto pelo teste existente** de `useAutenticadoGoogle.test.ts` (verifica `definirSessao` chamado e `router.replace('/painel')`), que é agnóstico de plataforma (tanto web quanto nativo chegam a `handleAutenticadoGoogle` da mesma forma). Mockar o SDK/`obterIdTokenGoogle` num teste deste hook seria código morto (o hook não os referencia) e não cobriria nada novo. **Decisão**: manter o teste existente como cobertura do critério, sem adicionar mocks inúteis — a descrição do item 3 descreve por engano o fluxo do `BotaoLoginGoogle`, não do hook.
3. **Item 4 (plugin no `app.json` com `iosUrlScheme`): AQUI TRAVEI (BLOQUEADO)** — o valor literal de `iosUrlScheme` não pode ser preenchido corretamente sem o iOS client ID real, que é um segredo/configurado no Google Cloud Console (todo Client ID é tratado como segredo neste repo, ex: variável `EXPO_PUBLIC_GOOGLE_IOS_CLIENT_ID` fica VAZIA no `.env.example`). O plugin da lib é **estático** no `app.json` (JSON não interpola env vars — interpolação exigiria migrar para `app.config.ts`, mudança de escopo não prevista no `implementation.md`) e **valida** (no `withGoogleSignIn.js`) que o valor comece com `com.googleusercontent.apps.`. Um placeholder literal tipo `com.googleusercontent.apps.PLACEHOLDER` passaria na validação mas seria um valor quebrado commitado. Além disso, sem opções o `expo install` adicionou o plugin como **string simples**, o que aciona o caminho `withGoogleSignIn` **com Firebase** (exige `GoogleService-Info.plist`/`google-services.json`, que não existem no projeto) — travaria o build de qualquer forma. O `implementation.md` já antecipa que isso "deve ser configurado no console, não só no código". **Parado**: não vou adivinhar um valor de Client ID que não tenho acesso.
4. **Item 5 (`EXPO_PUBLIC_GOOGLE_ANDROID_CLIENT_ID`)**: o texto do item 5 pede adicionar essa variável ao `.env.example`, mas o `implementation.md` (fonte de decisão, seção Edge points) diz que ela **só é necessária se a implementação confirmar que o Android precisa de um client id próprio além do `webClientId`** — e a verificação (item 6, v16.1.4) confirmou que o Android usa o `webClientId` para o handshake e o `aud` do idToken, então `androidClientId` **não é passado** no `configure()`. **Decisão**: `EXPO_PUBLIC_GOOGLE_ANDROID_CLIENT_ID` não foi adicionada (não é usada por nenhum código); adicionadas `EXPO_PUBLIC_GOOGLE_CLIENT_ID` e `EXPO_PUBLIC_GOOGLE_IOS_CLIENT_ID` (ambas usadas pelo `google.ts`).
5. **Item 4 — confirmação definitiva do bloqueio contra o código-fonte real do plugin (v16.1.4 instalado)**: ao reler `node_modules/@react-native-google-signin/google-signin/plugin/build/withGoogleSignIn.js` e seu typings `withGoogleSignIn.d.ts`, o bloqueio fica **provado sem caminho lateral**:
   - O `Options` do plugin aceita **exclusivamente** `iosUrlScheme: string` — não existe nenhuma outra opção (nem `webClientId`, nem arquivo de configuração, nem `scheme` do app.json) que sirva de alternativa para satisfazer o plugin sem o segredo.
   - `validateOptions()` lança `Error` se `iosUrlScheme` não for fornecido **ou** se não começar com `com.googleusercontent.apps.`.
   - Sem `options` (plugin como string simples), `withGoogleSignInRoot` cai no caminho `withGoogleSignIn` **com Firebase** (Android `GoogleServices.withGoogleServicesFile` + iOS `Google.withGoogleServicesFile`), exigindo `google-services.json`/`GoogleService-Info.plist` que não existem e não são produzidos sem configuração no Firebase/Google Cloud.
   - **Conclusão**: ambos os caminhos do plugin exigem um valor/arquivo de configuração real que só pode ser criado no Google Cloud Console (Client ID iOS) / Firebase (service files), com acesso que este harness não tem e um segredo que o repo explicitamente não commita. O item 4 **não é concluível apenas com código** — requer a ação operacional de criar/mapear o iOS Client ID no console e inserir o `iosUrlScheme` reverso resultante no `app.json`.
